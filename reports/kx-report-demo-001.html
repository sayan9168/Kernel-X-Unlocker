## Abstract

This audit characterises the kernel-level security posture of a **Samsung SM-G986B** running Android 11 (SDK 30) on a **Samsung Exynos** SoC with Linux kernel `5.10.134-013.15.kangaroo.al8.x86_64` (non-GKI / vendor kernel). Static telemetry was mapped against a curated knowledge base of 20 publicly documented vulnerability surface areas, yielding a normalized risk score of **9.38/10.0 (CRITICAL)**. 5 dry-run scenario batteries were executed to model FBE, keystore-policy and credential-verifier boundary behaviour. No live attack path was exercised or attempted.

## 1. Methodology

1. **Telemetry acquisition** — read-only collection of `/proc/version`, `/proc/cpuinfo`, `/sys/devices/soc0/*`, `/proc/cmdline`, kernel config (`/proc/config.gz` or `/boot/config-*`) and Android properties (`getprop` or injected lab dictionary).
2. **Surface correlation** — kernel series + subsystem configuration matched against the local CVE knowledge base; tri-state applicability (present / absent / unverifiable).
3. **Scoring** — `impact × reachability × exploit-maturity × applicability × patch-decay`, complement-aggregated and mitigation-adjusted (formula in Appendix A).
4. **Dry-run modelling** — declarative scenarios exercise the in-process keystore/FBE/Gatekeeper state machines; only policy outcomes are recorded.
5. **Reporting** — canonical JSON + Markdown export with integrity digest and citations.

## 4. Recommendations (defensive)

1. Track the latest Android Security Bulletin and OTA baseline; patch age is the single strongest predictor of aggregate kernel exposure.
2. Prioritize monitoring/verification for the highest-contributing subsystems: core-mm-numa, core-mm-pipe, ebpf-verifier, exynos-lpa.
3. Verify the 2022-03 (Dirty Pipe) fix is present in the running kernel build via the vendor changelog rather than the version string alone.
4. Prefer builds that replace legacy ION with dma-buf heaps and constrain heap access with SELinux genfs contexts.
5. Set kernel.unprivileged_bpf_disabled=1 (or 2 on >= 5.8) and restrict BPF program loading to trusted domains.
6. Re-lock the bootloader for production evaluation units: an unlocked device invalidates AVB trust assumptions across the whole assessment.
7. Restore/verify the AVB chain-of-trust (vbmeta digest, rollback protection indexes) before drawing conclusions about boot-path integrity.
8. All findings are *candidates* derived from static version/config correlation; confirm each via vendor source changelogs before publication.

## Appendix A — Scoring Model

```
contribution_i = Impact_i × Reachability_i × Maturity_i × Applicability_i × PatchDecay
Impact_i         = clamp(6.42 × ISCBase_i, 1, 10)      # CVSS 3.1 subscore approximation
Reachability_i   = clamp(AV × AC × UI / 0.85, 0.15, 1)
RiskScore        = clamp(10 × (1 − Π(1 − contribution_i / 10)) × (1 + ΣCredit), 0, 10)
```

Reports embed an environment hash and a knowledge-base digest. Re-running the
same toolkit build against the same fingerprint input reproduces byte-identical
canonical JSON (modulo wall-clock fields), enabling third-party replication of
the quantitative sections.
